# Plan de Arquitectura y Migración Enterprise para BotSAC

Este documento define la estrategia para evolucionar BotSAC desde su almacenamiento local (JSON/SQLite) hacia una arquitectura empresarial altamente escalable, utilizando **Oracle Database**, un backend estructurado mediante API REST y una infraestructura contenida en **Docker**.

Este plan está diseñado para ser revisado por tu **AI Architect** y las instrucciones de base de datos están listas para tu **DBA**.

---

## 1. Fases del Plan de Trabajo (Para el AI Architect)

La migración y paso a producción se dividirá en 4 fases estratégicas para asegurar una transición sin disrupciones en la operación actual.

### Fase 1: Arquitectura de Datos y Esquema Oracle (Semana 1)
*   **Objetivo:** Trasladar la carga cognitiva y de almacenamiento a los servidores Oracle.
*   **Tareas:**
    *   Ejecución del script DDL por parte del DBA (ver sección 2).
    *   Creación de usuarios, roles y asignación de cuotas de tablespace.
    *   Pruebas de conectividad desde el entorno de desarrollo usando `oracledb` (driver oficial de Oracle para Python).

### Fase 2: Desarrollo del Backend API (Semana 2)
*   **Objetivo:** Reemplazar el manejo directo de archivos por una API robusta y segura.
*   **Tareas:**
    *   Implementar **FastAPI** (Python) como middleware entre la BD Oracle y el Frontend.
    *   Mapear las tablas de Oracle utilizando un ORM (como SQLAlchemy).
    *   Crear los endpoints REST: `/api/radicados`, `/api/documentos`, `/api/metricas`, `/api/sync`.
    *   Integrar los scripts de scraping (`sync_aprobaciones.py`) directamente como *Background Tasks* o Workers (ej. Celery) que escriban directo a Oracle.

### Fase 3: Refactorización del Frontend y Conexión (Semana 3)
*   **Objetivo:** Conectar la interfaz de React (Vite) al nuevo Backend API.
*   **Tareas:**
    *   Actualizar `api.ts` en el frontend para apuntar a la URL del nuevo backend en lugar del servidor de desarrollo local.
    *   Adaptar las interfaces de TypeScript (`types/index.ts`) si hay algún cambio leve en los nombres de las columnas que provienen de Oracle.

### Fase 4: Dockerización y Despliegue CI/CD (Semana 4)
*   **Objetivo:** Empaquetar la aplicación para su ejecución agnóstica en los servidores.
*   **Tareas:**
    *   Crear un `Dockerfile` multietapa para el Frontend (construcción con Node, servicio con Nginx).
    *   Crear un `Dockerfile` para el Backend Python (instalando el Oracle Instant Client si es necesario).
    *   Diseñar un archivo `docker-compose.yml` que orqueste ambos servicios y los exponga a través de un proxy reverso seguro.

## 2. Instrucciones DDL para el DBA (Modelo Relacional Oracle)

**Nota para el DBA:** 
El siguiente script define el esquema relacional principal diseñado para almacenar los radicados, la estructura documental, metadatos extraídos por la IA y la trazabilidad. Se utilizan tipos de datos optimizados para texto masivo (`CLOB`) pensando en las respuestas generadas y los contextos de los documentos.

```sql
-- ==========================================
-- SCRIPT DE CREACION DE ESQUEMA PARA BotSAC
-- Motor: Oracle Database
-- ==========================================

-- 1. Tabla Principal de Radicados (Casos SAC)
CREATE TABLE SAC_RADICADOS (
    ID_RADICADO VARCHAR2(50) PRIMARY KEY,
    ASUNTO VARCHAR2(500) NOT NULL,
    MUNICIPIO VARCHAR2(150),
    FUNCIONARIO_ASIGNADO VARCHAR2(150),
    REMITENTE VARCHAR2(150),
    CATEGORIA VARCHAR2(100),
    FECHA_CREACION TIMESTAMP,
    FECHA_VENCIMIENTO TIMESTAMP,
    ESTADO_SAC VARCHAR2(50),
    ESTADO_BOTSAC VARCHAR2(50) DEFAULT 'POR_GESTIONAR', -- POR_GESTIONAR, EN_PROCESO, FALTA_APROBACION, FINALIZADO
    RESUMEN_CONTEXTO CLOB, -- Para manejar el contexto y armado de respuestas de la IA
    RESPUESTA_SUGERIDA CLOB,
    ES_VENCIDO NUMBER(1,0) DEFAULT 0,
    CREATED_AT TIMESTAMP DEFAULT SYSTIMESTAMP,
    UPDATED_AT TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- 2. Tabla de Instituciones y Sedes asociadas al radicado
CREATE TABLE SAC_SEDES_AFECTADAS (
    ID_SEDE NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ID_RADICADO VARCHAR2(50) NOT NULL,
    NOMBRE_INSTITUCION VARCHAR2(255),
    MUNICIPIO VARCHAR2(150),
    NOMBRE_SEDE VARCHAR2(255),
    CONSTRAINT FK_SEDE_RADICADO FOREIGN KEY (ID_RADICADO) REFERENCES SAC_RADICADOS(ID_RADICADO) ON DELETE CASCADE
);

-- 3. Tabla de Documentos adjuntos (Para análisis de la IA)
CREATE TABLE SAC_DOCUMENTOS (
    ID_DOCUMENTO VARCHAR2(100) PRIMARY KEY,
    ID_RADICADO VARCHAR2(50) NOT NULL,
    NOMBRE_ARCHIVO VARCHAR2(255) NOT NULL,
    TIPO_DOCUMENTO VARCHAR2(50), -- PDF, DOCX, IMG
    NUM_PAGINAS NUMBER,
    HASH_SHA256 VARCHAR2(64),
    RESUMEN_DOCUMENTO CLOB,
    ES_PROCESADO NUMBER(1,0) DEFAULT 0,
    FECHA_CARGA TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT FK_DOC_RADICADO FOREIGN KEY (ID_RADICADO) REFERENCES SAC_RADICADOS(ID_RADICADO) ON DELETE CASCADE
);

-- 4. Tabla de Hallazgos extraídos por la IA
CREATE TABLE SAC_HALLAZGOS (
    ID_HALLAZGO NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ID_RADICADO VARCHAR2(50) NOT NULL,
    ID_DOCUMENTO VARCHAR2(100),
    HECHO_EXTRAIDO CLOB NOT NULL,
    NIVEL_RELEVANCIA VARCHAR2(20), -- ALTA, MEDIA, BAJA
    FECHA_EXTRACCION TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT FK_HALLAZGO_RADICADO FOREIGN KEY (ID_RADICADO) REFERENCES SAC_RADICADOS(ID_RADICADO) ON DELETE CASCADE,
    CONSTRAINT FK_HALLAZGO_DOC FOREIGN KEY (ID_DOCUMENTO) REFERENCES SAC_DOCUMENTOS(ID_DOCUMENTO) ON DELETE SET NULL
);

-- 5. Tabla de Alertas Automáticas
CREATE TABLE SAC_ALERTAS (
    ID_ALERTA NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ID_RADICADO VARCHAR2(50) NOT NULL,
    TIPO_ALERTA VARCHAR2(100) NOT NULL, -- ej. "Vencimiento Próximo", "Falta Firma"
    DETALLE VARCHAR2(500),
    SEVERIDAD VARCHAR2(20), -- CRITICA, ADVERTENCIA, INFO
    ESTADO_ALERTA VARCHAR2(20) DEFAULT 'ACTIVA',
    CONSTRAINT FK_ALERTA_RADICADO FOREIGN KEY (ID_RADICADO) REFERENCES SAC_RADICADOS(ID_RADICADO) ON DELETE CASCADE
);

-- 6. Tabla de Trazabilidad y Logs del Bot
CREATE TABLE SAC_TRAZABILIDAD (
    ID_TRAZA NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ID_RADICADO VARCHAR2(50) NOT NULL,
    ACCION VARCHAR2(255) NOT NULL, -- ej. "Extracción Iniciada", "Lectura de Documento"
    ORIGEN VARCHAR2(50), -- "BOT_SCRAPER", "IA_ANALYZER", "USUARIO"
    DETALLE CLOB,
    FECHA_EVENTO TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT FK_TRAZA_RADICADO FOREIGN KEY (ID_RADICADO) REFERENCES SAC_RADICADOS(ID_RADICADO) ON DELETE CASCADE
);

-- Indices para optimizar las consultas del Dashboard
CREATE INDEX IDX_RADICADOS_ESTADO ON SAC_RADICADOS(ESTADO_BOTSAC);
CREATE INDEX IDX_RADICADOS_FECHAS ON SAC_RADICADOS(FECHA_CREACION DESC);
CREATE INDEX IDX_RADICADOS_VENCIDOS ON SAC_RADICADOS(ES_VENCIDO);
```

## 3. Arquitectura Docker Propuesta (High Level)

Una vez que la BD Oracle esté lista, la infraestructura se orquestará con un `docker-compose.yml` que contendrá:

1.  **Contenedor Frontend (Vite/React + Nginx):**
    *   Construido y minificado, servido por Nginx en el puerto 80/443.
    *   No tiene lógica pesada, solo se comunica con la API.
2.  **Contenedor Backend API (FastAPI + Python 3.12):**
    *   Contendrá la librería `oracledb` (Thin mode, no requiere cliente de instalación pesado).
    *   Contendrá todo el modelo de Pydantic/SQLAlchemy.
    *   Expone Swagger/OpenAPI automáticamente para el equipo de desarrollo.
3.  **Contenedor Worker (Celery/Python Scraper):** *(Opcional pero recomendado)*
    *   Un contenedor aislado encargado única y exclusivamente de ejecutar el Playwright de manera asíncrona para no bloquear el backend principal, conectándose a Oracle para reportar el progreso.
