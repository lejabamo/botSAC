# BotSAC Enterprise: Especificación de Datos y Modelo Relacional (DBA-Ready)

Este documento contiene el diseño arquitectónico final y ajustado de la base de datos para **BotSAC Enterprise**. Está diseñado para garantizar una auditoría inquebrantable, versionamiento robusto, y separación absoluta de responsabilidades.

**Nota para el DBA:** El DDL está formulado para **Oracle AI Database 26ai / versión Oracle institucional soportada**. Por favor confirme la versión exacta instalada en sus servidores antes de ejecutar el script para aprovechar optimizaciones específicas si estuvieran disponibles.

---

-- REGULADOR DB: Garantizar que la Memoria sólo provenga de respuestas aprobadas
CREATE OR REPLACE TRIGGER TRG_CHK_MEMORIA_APROBADA
BEFORE INSERT OR UPDATE ON SAC_MEMORIA_INSTITUCIONAL
FOR EACH ROW
DECLARE
    v_estado VARCHAR2(20);
BEGIN
    SELECT ESTADO_RESPUESTA INTO v_estado 
    FROM SAC_RESPUESTAS 
    WHERE ID_RESPUESTA = :NEW.ID_RESPUESTA_ORIGEN;
    
    IF v_estado != 'APROBADA' AND v_estado != 'PUBLICADA' THEN
        RAISE_APPLICATION_ERROR(-20001, 'Integridad violada: La Memoria Institucional sólo puede derivarse de Respuestas en estado APROBADA o PUBLICADA.');
    END IF;
END;
/

## 3. Diccionario de Datos y Reglas de Integridad

*   **Identificación Estable:** El municipio utiliza ahora `CODIGO_DANE_MUNICIPIO` para joins estructurales, reservando `MUNICIPIO_HISTORICO` para snapshots temporales. Igual tratamiento recibe el funcionario (`ID_USUARIO_ASIGNADO` vs `NOMBRE_FUNCIONARIO_HIST`).
*   **Mantenimiento de Materializadas (`ES_VENCIDO`):** Para favorecer la lectura instantánea en la bandeja de entrada, el estado de vencimiento se consolida como materializado. *Regla Arquitectónica:* Debe ser actualizado rutinariamente mediante un cron job del worker de Procesamiento o interceptado transaccionalmente por el servicio de API de creación/asignación.
*   **Relaciones Polimórficas Delegadas:** Las relaciones `<ENTIDAD>_FUENTES` (p. ej. `SAC_CONTEXTO_FUENTES`) utilizan llaves lógicas (`TIPO_FUENTE` + `ID_FUENTE`) para evitar la explosión de N tablas pivotales. *Regla de integridad:* La capa de servicio (API/Middleware) es el responsable exclusivo de la consistencia y borrado en cascada (soft delete) lógico de estas uniones, no la base de datos Oracle.

---

## 4. Estrategia de Hashes (Diferenciación Canónica)

*   **HASH_CONTENIDO:** Es la huella digital inmutable que certifica únicamente el texto o el archivo. Garantiza que la respuesta redactada, el documento original, o el hallazgo no ha sido alterado. 
    *   *Regla:* `hash( TEXTO_EN_UTF8 )`. ¡No depende del estado ni del autor!
*   **HASH_REGISTRO (Versiones):** Presente en entidades mutables como Respuestas. Es la firma del snapshot total.
    *   *Regla:* `hash( ID_RADICADO + VERSION + HASH_CONTENIDO + ID_AUTOR )`. Esto protege toda la transacción que formó esa versión en particular.

---

## 5. Estrategia de Versionamiento y Memoria

*   **Trazabilidad Continua:** Ningún registro de texto se sobrescribe. Toda respuesta pasa por `BORRADOR` ➔ `EN_REVISION` ➔ `APROBADA` generando saltos de versión inmutables y documentables, protegiendo las acciones de la IA frente a las intervenciones humanas.
*   **Candado de Memoria (Trigger):** Mediante el trigger `TRG_CHK_MEMORIA_APROBADA` alojado en el motor de base de datos, es imposible matemática y estructuralmente que una respuesta genere una plantilla institucional si no se certifica primero en los estados "APROBADA" o "PUBLICADA".

---

## 6. Estrategia de Migración (Orden DBA)

1.  Migrar Catálogos y Entidades Raíz: `SAC_USUARIOS`.
2.  Importar Casos: `SAC_RADICADOS` y `SAC_SEDES_AFECTADAS`.
3.  Migrar Almacenamiento Lógico: `SAC_DOCUMENTOS` y `SAC_DOCUMENTOS_DERIVADOS`.
4.  Consolidar IA (Datos pasados): `SAC_EXTRACCIONES_DOCUMENTO` ➔ `SAC_EVIDENCIAS` ➔ `SAC_HALLAZGOS`.
5.  Versionar Resultados: `SAC_CONTEXTO_VERSIONES` y `SAC_RESPUESTAS` (Insertando los datos heredados del JSON como V1).
6.  Inicializar Auditoría: Poblar `SAC_TRAZABILIDAD` y reconectar jobs in-flight en `SAC_PROCESAMIENTO`.
